A research agent for materials science.

MatAgent retrieves and reads the literature, identifies missing data, and formulates hypotheses screened by chemical-validity checks. Each workflow run is saved with its inputs, outputs and events for review.

02

Five modules, four capability groups

MatAgent's modes are built on five core modules: SEARCH, PLAN, AUGMENT, DISCOVER and EVALUATE. Most of its modes fall into four capability groups.

1Knowledge acquisition

Searches the literature for the gaps in your database, finds existing libraries and tools, reads documents as text and page images, and ingests structured knowledge into the database.

Method GAR 2.1 gap-driven search · SE 7.3 GitHub, PyPI · MMR 4.1⁠–⁠4.3 text and page-image RAG · KC 6.1⁠–⁠6.4

2Knowledge reasoning and analysis

Compares the values that different sources report, formulates and ranks hypotheses, and reasons over a knowledge graph with GNN-enhanced retrieval.

Method LCA 5.1 relative deviation · HF 8.1⁠–⁠8.4 · MMR 4.4⁠–⁠4.8 multi-hop paths in a knowledge graph

3Computational planning

A language model drafts computational study designs from database records or from documents; rule-based checks drop invalid steps, and CDTP 3.3 also scores the plan's feasibility.

Method CDTP 3.1 database-informed · 3.2 document-driven · 3.3 feasibility score (FS) · fallback: rule-based plan

4Self-enhancement and expansion

Generates code modules and agent modes from a description, checks that they run and pass their tests, assesses their readiness for use, and optimises code with OpenEvolve.

Method SE 7.1, 7.2, 7.4 · sandboxed tests · readiness score (ARS) · OpenEvolve fitness: syntax, imports, tests, lint, types

03

Reads the literature

MatAgent searches paper indexes, ranks the results, and answers from page text and page images, citing pages. With a knowledge graph, a graph neural network reasons over multi-hop paths.

Finds and ranks papers

Each request becomes up to five search queries. The results are merged and ranked, and the top papers are downloaded.

Method LR 1.1 · Semantic Scholar, Google Scholar (with the scholarly package), arXiv fallback · lexical rank: title, abstract, recency, citations

Answers cite the page

Ask a question of a paper: the best-matching passages are retrieved, and a language model answers from them, citing pages as [p. N].

Method MMR 4.1⁠–⁠4.3 · BM25 over overlapping ~1,200‑character page‑text chunks · top k, at most two per page

Reads charts and images

Page images are read by default, alongside the text: the pages are ranked, and a vision-language model reads the best-matching ones, charts and images included.

Method MMR 4.1⁠–⁠4.3 · ColSmol‑500M ranks page images · each page reading, labelled [p. N], goes to the language model

Reasons over a knowledge graph

Given a knowledge-graph source, a graph neural network reasons over multi-hop paths in the graph to retrieve evidence for the answer.

Method MMR 4.4⁠–⁠4.8 · GNN‑enhanced retrieval · knowledge‑graph reasoning over multi‑hop paths · graph or hybrid (PDF plus graph) retrieval

One searchable knowledge base

Papers with their figures, mode runs, datasets, chat answers and Deep Research reports share one index. A vision-language model writes figure descriptions, labelled model-generated.

Method SQLite FTS5 BM25 + sqlite‑vec vector search (OpenAI embeddings), merged by reciprocal rank fusion · BM25 only without embeddings

Deep Research, plan first

A language model drafts a plan of sub-questions and the sources for each. You can edit the plan; the research starts only when you press Start.

Method quick / standard / deep: ≤ 3 / 6 / 10 sub‑questions, 0.4 / 1.2 / 3 M tokens · stopped early: partial report from findings, if any

04

Finds what is missing

MatAgent lists gaps in the data, asks a language model whether retrieved papers close the literature gaps, and compares the values that sources report for the same property.

Gaps found by rules

Gaps are collected without a language model: from database coverage, the domain's gap checklist, and the database query's gap list. A few of their terms join the paper search.

Method GAR 2.1 · a checklist category stays open unless ≥ 2 reviewed records match it · record‑count gaps listed separately

Closure judged against papers

In one call, a language model decides whether any retrieved paper closes each gap. It must name the paper and quote it; the quote is not checked against the abstract.

Method ≤ 10 papers: title + first 600 abstract characters (defaults) · closure score (GCS) = 100 × closed ÷ judged · fallback: word overlap

Shows where sources disagree

Values with units are pulled from each source's summary by pattern matching and compared in pairs per property. On conflict, a language model re‑extracts them, when one is available.

Method LCA 5.1 · |a−b| ÷ max(|a|,|b|): ≤ 1 % consensus, ≤ 10 % partial (adjustable), else contradiction · incompatible units not compared

05

Formulates hypotheses

Seven language-model generators propose candidates. Rule-based checks screen them; a language model reviews the rest against retrieved evidence, then compares them in pairs.

Seven generators

Seven language-model prompts propose candidates: inspiration, assumption hop and analogy, plus four data-driven ones that add statistics from database records or an LCA result.

Method quick: inspiration · standard: + assumption hop, analogy · deep: all seven (contradiction needs an LCA result)

Rule-based checks before review

Before language-model judgement, gates reject candidates that fail a hard check, including chemical rules for their material class when an identifier is given. Soft checks only lower the rank.

Method hard: SMILES sanitisation · valid IZA code · Si/Al ≥ 1 (Löwenstein's rule) · composition sum ≤ 101 % · soft: charge balance, radius mismatch

Reviewed against the evidence

A language model weighs each candidate against up to eight retrieved passages; “supports” and “disproved” stand only with a verbatim quote. A critic language model rates flaws.

Method quoted “disproved” rejects · flaws fatal / major / minor → score 1⁠–⁠5 · a fatal flaw rejects, unless none would remain

Compared head-to-head

A language-model judge compares candidates in pairs, blind to IDs, generator and lineage. A pair is won only if won in both presentation orders; a split is a tie.

Method Bradley⁠–⁠Terry fit, bootstrap intervals · order: gate, critic score, flaws, soft checks, then strength

Bounded effort

Each run has an effort tier that caps language-model calls and run time.

Method quick / standard / deep: ≤ 24 / 150 / 400 calls, 300 / 1,200 / 3,600 s · retrieval time not counted

A benchmark from recent papers

44 cases from 2026 papers across 10 domains test whether the top hypotheses recover each paper's key points. A language model drafted the key points; human spot-check is pending.

Method recall@3 by a language‑model matcher · branch vs base: paired‑bootstrap 95 % CI of Δrecall@3, lower bound > −0.05 · run by hand

06

Drafts computational study designs

A language model drafts a study design, with suggested parameters, from the request and any database records or from page-cited excerpts. Rule-based checks drop failing steps.

Drafted by a language model, checked by rules

A language model drafts 3–6 steps, each with a task, method, system, purpose, gap, evidence and core-hours. Steps naming an unlisted gap or a page outside the excerpts are dropped.

Method also dropped: missing task, method or purpose · core‑hours outside 1⁠–⁠200,000 (the model's own estimate)

From the request or from documents

Without documents, it plans from the request and any database records PLAN found, and the model is asked to name 2–5 gaps. With documents, it plans from page-cited excerpts.

Method CDTP 3.1: request + records, no page citations · CDTP 3.2: page‑cited excerpts · CDTP 3.3: 3.2 if documents are given, else 3.1

A labelled fallback

If fewer than two valid steps remain, no language model is available, or a document run has no cited evidence, the plan stays PLAN's rule-based template, labelled as such.

Method labelled template, with the reason · CDTP 3.1 that also found no records: marked partial

Parameters and feasibility

The study design includes suggested parameters for its steps. CDTP 3.3 then scores the plan's feasibility (FS), assessing resources and tools: a model-assisted measure of the run's own output.

Method FS: CDTP 3.3 only · core-hours summed; timeline ⌈total ÷ 2,000⌉ weeks

07

Prepares and runs VASP workflows

MatAgent prepares VASP inputs for your review, builds slabs with adsorbates, and runs NEB, equation-of-state and DOS workflows on a Slurm cluster once you approve the run.

Inputs returned for review

Each step writes INCAR from a workflow preset, plus POSCAR and KPOINTS, and returns the run folder. POTCAR is assembled on the cluster from your licensed set.

Method ENCUT = 1.3 × max ENMAX · KPOINTS: Γ‑centred mesh · PBE, PBEsol, SCAN or r2SCAN · job script for Slurm

Slabs and adsorbates

From a bulk structure, a Miller index and an adsorbate, VW 9.4 builds the slab, places the adsorbate on a site and computes the adsorption energy from three calculations.

Method E(slab+ads) − E(slab) − E(molecule) · defaults: slab ≥ 10 Å, vacuum 15 Å, first ontop site · your structures override

Runs after your approval

With the Slurm backend, nothing reaches the cluster until you approve the run. Steps are submitted in order over SSH and tracked through Slurm's states.

Method one approval per run: steps, first inputs, Slurm profile, core‑hour ceiling · off‑plan step: asks again · failed job: no resubmit

Parsed results

Outputs are fetched and parsed. NEB images are interpolated between relaxed end points; EOS energies are fitted with the Birch–Murnaghan equation; DOS is read from DOSCAR.

Method NEB: IDPP images, climbing image, barrier = max E(image) − E(IS) · EOS: V₀, E₀, B₀, B₀′ · DOS: Fermi level, band gap

08

Ten material domains

Each material domain sets the chemical checks that screen hypotheses, adds design rules to the hypothesis prompt, and gives gap analysis a domain checklist.

Design rules in the prompt

Each domain profile adds 11–14 design rules and one review criterion. The prompt asks the language model to cite a rule for each change; nothing enforces it.

Method criterion, e.g. zeolite: framework synthesisability · catalyst: stability under operation · no rule fits: empty list + reason

Keywords and gap categories

Each domain adapter defines keywords, used to infer the domain from a request, and gap categories for the gap checklist. The study designer is told the domain.

Method domain adapters · GAR 2.1: domain gap checklist · CDTP: domain in the designer prompt

09

Scores its own output

Nine modes end with one of six EVALUATE scores, computed from the run's own output: gap closure, RAG coverage, hypothesis formulation, plan feasibility, ingestion completeness or tool readiness.

Judge, formula, weighted sum

A language model judges whether the papers it read close each gap (GCS); a formula counts terms in an analysis's text (RCS); HFS weights five dimensions of each hypothesis record.

Method GCS 100 × closed ÷ judged, fallback: word overlap · RCS coverage ≤ 40 + specificity ≤ 35 + calibration ≤ 25

Feasibility, ingestion and readiness

FS assesses a plan against available resources and tools, ICS how complete an ingestion is, and ARS whether a newly created tool is ready for use.

Method FS: CDTP 3.3 · ICS: KC 6.2, 6.4, ingested ÷ expected · ARS: SE 7.2, only with test and security results

Measures, not verdicts

Every score is a model-assisted measure of a run's own output; each runs 0–100 but has its own method, so scores are not comparable.

Method missing inputs give “unavailable”, not 0 (GCS, RCS, FS, ICS, ARS) · no independent check of the run

10

On the record, under your control

Runs follow the limits you set on database writes, failed steps and output checks. Costly chat actions wait for your confirmation, and workflow runs are stored for replay and review.

Run controls you set

You set how runs may write to the database, what happens when a chained step fails, whether partial results are kept, and which checks outputs must pass.

Method write protection: full / append‑only / read‑only · failed step: halt, ask (pause for review, then re‑run) or skip · post‑run output checks

Costly actions wait for you

Chat actions marked costly or destructive, such as starting an improvement run, run only after you confirm an approval card, with exactly the parameters shown.

Method held as a proposal until confirmed · the confirmed parameters are bound to that proposal

Each workflow run is recorded

Each workflow run is stored with its input, checkpoint, results and events; a chained run's results hold each step's outputs and metrics. You can pause, resume, cancel or replay it.

Method input stored with secrets redacted · a checkpoint after each step · a report from the record · records indexed in the knowledge base

Memory, kept for review

Rules turn mode-run events into facts, and a language model derives lessons from a run's events. New facts are checked for contradictions. Stored lessons are listed for you to review.

Method contradiction check: embedding similarity, then keyword and numeric checks · periodic consolidation by a language model

11

Improves and extends itself

Improvement runs test proposed changes against a baseline, and nothing becomes active without an administrator's approval. DISCOVER also finds libraries, writes new modules and evolves code.

Active only after approval

A language model proposes prompt, setting, code or workflow edits, scored on a select split, up to three on a holdout split. An administrator must approve before any becomes active.

Method top third of 12 → select split → ≤ 3 on holdout · to review if CI low > baseline mean + margin, or (tier) no worse and ≥ 10 % cheaper

Strategies compared under one call cap

The Algorithm Arena runs several improvement strategies on the same task suite, each under the same maximum call budget, and compares their best variants on the holdout split.

Method 3 seeds by default (1⁠–⁠5) · bootstrap intervals

Edits to DISCOVER end as a git branch

A language model edits DISCOVER's code-generation program; candidates run sandboxed and are scored by hidden tests. Approving a winner writes one commit on a new local git branch.

Method sandbox‑exec: macOS only · nothing pushed or merged · production keeps the checked‑in program

Finds existing libraries

Before writing code, DISCOVER searches a curated registry, PyPI and GitHub for existing Python libraries and ranks the results by relevance.

Method GitHub token optional · a source that fails is listed with its error

Writes new modules

From a plain-language description, including integrations with chemistry software, DISCOVER writes a module with its tests. Checks run, the tests run in a sandbox, and passing files are staged.

Method type, lint and contract checks in strict mode · readiness (ARS) only with test and security results

Evolves code with OpenEvolve

SE 7.4 evolves a module's code over five island populations, 50 iterations by default, and records the best program. It needs an Anthropic API key.

Method fitness 0.2 syntax + 0.2 imports + 0.3 tests + 0.15 lint + 0.15 types · tests only in an isolated runner

12

Data and interfaces

Public datasets, your own files and records extracted from papers enter MatAgent's database. You work through chat; other agents call it through an MCP server.

Public datasets and your own files

Connectors import from Materials Project (with an API key), the Citrine MPEA alloy dataset, PolyMetriX polymer Tg data, Open Catalyst (downloaded or local files), and CSV, JSON or Excel uploads.

Method column mapping: fixed template for known source⁠–⁠database pairs, else a language model · a person reviews it before checks and writing

Records from papers

The knowledge-capture modes (KC 6.1–6.4) extract structured records from papers and ingest them into the database.

Method AUGMENT extracts the records · each is staged, checked, and merged if it passes; the run reports complete, partial or failed

Chat that shows structures

The chat agent uses tools and answers in typed blocks: text with citation chips, charts, diagrams, paper figures, structures, actions and research plans.

Method POSCAR, CIF, XYZ: 3D (3Dmol.js) · SMILES: 2D drawing (smiles‑drawer)

Connects to other agents

An MCP server exposes ten tools, split by effect, to other agents. A command-line requester sends signed job folders to the MAESTRO meta-orchestrator; only its owner approves jobs.

Method MCP: stdio, or SSE on 127.0.0.1 with per‑agent tokens · MAESTRO: detached JWS (Ed25519) over RFC 8785 canonical JSON

Your model access

Choose per provider (Anthropic, OpenAI): a subscription through the signed-in Claude Code or Codex command-line tool, or an API key. Embeddings and figure descriptions need an API key.

Method API key: tested with the provider, then kept in the macOS Keychain, or read from the environment
